New Design

db-type at a glance — same controller, three faces

🗄️
--db-type=local
MariaDB-backed

Existing production path. First-boot empty DB is auto-provisioned by setup_mysql_db_post.sh. Full persistence across restarts.

🚫
--db-type=none
Zero-DB, in-memory only

New. No SQL server needed at all. Controller synthesizes its own identity from the AL-SAP MAC via bootstrap_controller_network() on every boot.

☁️
--db-type=cloud
Remote-managed (planned)

Same db_client_t contract; execute() will forward to a cloud API instead of SQL. Design already accommodates it — no controller changes required.

⇄   Same data model · same orchestration · same 1905.1/M1-M2 logic — only db_client_t changes underneath
Motivation

Why the controller needs a pluggable DB backend

Problem

  • Controller always assumed a running MariaDB instance on box.
  • Dev/test rigs, CI, and lightweight deployments don't want to bring up a full SQL server.
  • Future targets (cloud-managed controllers) need config to live remotely, not locally.

Goal

  • Introduce a --db-type flag: local, none, cloud.
  • Keep one data-model / orchestration code path regardless of backend.
  • All persistence differences isolated behind a single abstract interface.

Command line

// launch controller against AL SAP with no database backend
/usr/bin/onewifi_em_ctrl bpi@root --db-type=none

// default: persist to MariaDB
/usr/bin/onewifi_em_ctrl bpi@root --db-type=local

Design requirement: m_db_client storage type

Introducing db_client_t as a pure abstract interface — the core of the new pluggable-backend design — means dm_easy_mesh_ctrl_t can only hold it as a pointer, so a concrete backend can be resolved and swapped in at runtime via db_client_create(db_type).

// a value member cannot work with an abstract interface
// error: cannot declare field to be of abstract type 'db_client_t'
db_client_t  m_db_client;   // invalid

// required declaration
db_client_t *m_db_client;

Deep Dive

db_client_none_t — a true no-op

Implementation

int db_client_none_t::init(const char *path) {
    // No backend to connect to - always succeeds.
    return 0;
}

void *db_client_none_t::execute(const char *query) {
    // Nothing to run against; no result set ever.
    return NULL;
}

bool db_client_none_t::next_result(void *ctx) {
    return false;
}

Why this is safe

  • db_easy_mesh_t::insert_row / update_row / delete_row now early-return on db_client.get_type() == db_client_type_none — the SQL string is never built at all.
  • No blocking I/O, no crash risk — every generic row-op path is naturally a no-op.
  • Zero special-casing needed in dm_<table>_list_t code for db-type; the abstraction absorbs it entirely.

Consequence

Because --db-type=none never persists anything, the controller starts with zero rows every boot. load_tables() always reports empty → the controller must synthesize its own identity in memory instead of loading it from a table.

Optimization: skip query-string construction too, not just execution

Originally insert_row/update_row/delete_row still built the full snprintf/vsnprintf SQL string on every call before handing it to execute(), even though the none backend discards it — wasted CPU cycles and stack traffic on every single row op. Guarding on get_type() == db_client_type_none at the top of each function skips that formatting entirely.

The in-memory write (put_network_ssid mutating dm_easy_mesh_t::m_network_ssid[]) always happens — regardless of db-type. Next Steps

Open items & recommendations

1. Auto-seed SSIDs for --db-type=none

Currently requires a manual CLI Reset. Consider having bootstrap_controller_network() optionally load /nvram/Reset.json directly (mirroring what setup_mysql_db_post.sh does for local), while still protecting the controller's real AL-SAP identity from the file's placeholder ControllerID.

2. db_client_cloud_t

Not yet implemented. Same db_client_t contract applies; execute() would translate to a remote API call instead of SQL or a no-op.

3. Guard against future identity overwrites

Add a safeguard in dm_network_list_t::update_list() (the db_update case) so a config-file-driven update can never clobber the controller's own bootstrapped ctrl_id once set.

4. Keep SSID_TRACE logs (behind a flag)

Useful for diagnosing DB-vs-in-memory divergence going forward; consider gating behind a debug/verbose flag before merging to develop.

Summary

Takeaways

1. One abstraction, three backends

All persistence differences are isolated inside db_client_t implementations. Data-model, orchestration, and TLV construction code never branch on db-type.

2. In-memory model is the source of truth

Whatever the backend, dm_easy_mesh_t's in-memory arrays (network, device, radios, SSIDs) are what the protocol layer reads from — the DB is only a mirror.

3. Bootstrap replaces load for --db-type=none

bootstrap_controller_network() synthesizes the controller's identity from the AL-SAP MAC every boot, since nothing is ever persisted.

4. Verified with targeted tracing

SSID_TRACE logs across update_tables → set_config → update_list → put_network_ssid confirmed identical behavior across backends, and a real agent successfully completed configuration end-to-end with --db-type=none.
