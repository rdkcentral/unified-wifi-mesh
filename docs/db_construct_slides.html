Overview

What is the Controller DB?

The EasyMesh controller maintains a full in-memory replica of the mesh topology and persists it to a relational database. This "data model" drives policy distribution, onboarding, and northbound TR-181 queries.

Persistence Backend

Single concrete db_client_t class wraps libmariadb (MYSQL *m_con). Owned by value inside dm_easy_mesh_ctrl_t — no factory, no polymorphism.

DB Persistence Layer

db_easy_mesh_t base class provides table init, CRUD, and JSON serialisation for every entity type.

Domain Model

dm_easy_mesh_ctrl_t inherits all list classes to form a single unified data model for the whole mesh network.

Key design goal: Keep persistence logic out of orchestration code — entity list classes receive db_client_t& by reference, so the controller core never embeds SQL directly.

Multiple Inheritance

All list classes are inherited by dm_easy_mesh_ctrl_t via C++ MI, giving a single object that owns all tables simultaneously.

Value Ownership

db_client_t is a value member of dm_easy_mesh_ctrl_t. All list-class methods receive it by reference (update_db(m_db_client, …)). No heap allocation or factory on this branch.

Per-Entity dm_*_t Objects

Entity instances (dm_radio_t, dm_bss_t, dm_sta_t …) hold the domain structs and are held by dm_easy_mesh_t containers in a list/hash.

db_client_t — Strategy Interface

// inc/db_client.h — concrete MariaDB class
class db_client_t {
  MYSQL *m_con;         // MariaDB connection
  int connect(const char *path);
public:
  int    init(const char *path);   // format: "user@password"
  void*  execute(const char *query);
  bool   next_result(void *ctx);
  char*  get_string(void *ctx, char *res, unsigned int col);
  int    get_number(void *ctx, unsigned int col);
  int    recreate_db();
  db_client_t();
  ~db_client_t();
};

// inc/dm_easy_mesh_ctrl.h — owned by value
class dm_easy_mesh_ctrl_t : ... {
  db_client_t m_db_client;  // value, not pointer
};

// Usage in table code (direct, no dereference)
dm_network_list_t::load_table(m_db_client);
dm_radio_list_t::update_db(m_db_client, op, data);

inc/db_client.h · inc/dm_easy_mesh_ctrl.h

Single Concrete Backend

One class handles everything: connection pooling via MYSQL *m_con (libmariadb), SQL execution, and result iteration. MySQL header is conditionally included for OpenWRT/RDKB (<mysql/mysql.h>) vs Debian (<mariadb/mysql.h>).

Value Ownership

m_db_client is held as a value member of dm_easy_mesh_ctrl_t. All list-class calls pass it by reference: update_db(m_db_client, …). No heap allocation; lifetime tied to the controller object.

Result Iteration Pattern

void* ctx = m_db_client.execute(query);
while (m_db_client.next_result(ctx)) {
  m_db_client.get_string(ctx, buf, col);
  m_db_client.get_number(ctx, col);
}

When next_result() returns false it frees ctx.

DB Persistence Layer

db_easy_mesh_t — Table Base Class

class db_easy_mesh_t {
public:
  db_table_name_t  m_table_name;   // e.g. "RadioList"
  unsigned int     m_num_cols;
  db_column_t      m_columns[EM_MAX_COLS];

  // Schema
  virtual void init_table();      // set m_table_name
  virtual void init_columns();    // populate m_columns[]

  // CRUD
  virtual int sync_db(db_client_t&, void *ctx);
  virtual int update_db(db_client_t&, dm_orch_type_t op, void *data);
  virtual bool search_db(db_client_t&, void *ctx, void *key);

  // JSON serialisation
  virtual int  set_config(db_client_t&, const cJSON *, void *parent_id);
  virtual cJSON* get_config(db_client_t&, void *parent_id);
};

Table Bootstrap

Each list class calls init() which runs init_table() + init_columns(), then issues CREATE TABLE IF NOT EXISTS … via db_client_t::execute().

Design Pattern

Entity + List Dual-Class Pattern

Every domain entity uses a two-class split: a pure-data entity class and a list/table class that adds DB persistence via multiple inheritance.

// 1. Pure domain data
class dm_radio_t {
  em_radio_info_t  m_radio_info;  // HAL struct
  int decode(const cJSON*, void*);
  cJSON* encode();
  em_radio_info_t* get_radio_info();
};

// 2. List + DB table
class dm_radio_list_t
  : public dm_radio_t
  , public db_easy_mesh_t
{
  void init_table() {
    snprintf(m_table_name, ..., "RadioList");
  }
  void init_columns() {
    m_columns[m_num_cols++] =
      db_column_t("RadioID", db_data_type_char, 17);
    // … 20+ more columns
  }
  int  sync_db(db_client_t&, void*);
  int  update_db(db_client_t&, dm_orch_type_t, void*);
  bool search_db(db_client_t&, void*, void*);
};

Benefit of the Split

  • Entity classes can be used on the agent (no DB) with zero overhead.
  • List classes extend entities with table schema and SQL logic — only compiled into the controller binary.
  • Agent-side code depends only on dm_radio_t, never on dm_radio_list_t.

Schema Deep-Dive

Core RF Topology Tables

RadioList

One row per radio per device

  • RadioID — RUID (MAC)
  • Band — 2.4 / 5 / 6 GHz
  • CF1, CF2 — centre frequencies
  • Utilization, Noise
  • NumberOfBSS
  • SteeringPolicy
  • RCPISteeringThreshold
  • STAReportingRCPIThreshold
  • TrafficSeparationCombined*
  • ChipsetVendor

BSSList

One row per BSS per radio

  • BSSID — BSS MAC
  • RUID → RadioList FK
  • SSID
  • Enabled
  • FronthaulUse, BackhaulUse
  • FronthaulAKMsAllowed
  • BackhaulAKMsAllowed
  • Profile1bSTAsDisallowed
  • Profile2bSTAsDisallowed
  • VlanID
  • EstServiceParameters{BE/BK/VI/VO}

STAList

One row per associated STA

  • MACAddress — STA MAC (PK)
  • BSSID → BSSList FK
  • RUID → RadioList FK
  • Associated flag
  • SignalStrength, RCPI
  • LastDataUplinkRate
  • LastDataDownlinkRate
  • PacketsSent, BytesSent
  • PacketsReceived, BytesReceived
  • RetransCount
  • FrameBodyLength + FrameBody — (re)assoc request, hex-encoded
Capability decode
HT/VHT/HE caps, SSID, supported rates are not persisted — they are derived on-demand from FrameBody by dm_sta_t::decode_sta_capability().
get_assoc_frame_ie_offset() probes for the correct IE start: assoc (4B fixed), reassoc (+6B current AP), or IEs-only layout.

Relationship chain: NetworkList → DeviceList → RadioList → BSSList → STAList  (hierarchy by ID composite keys, not explicit FK constraints in the schema)

init_tables() — Schema Bootstrap

void init_tables() {
  dm_network_list_t::    init();  // CREATE TABLE IF NOT EXISTS
  dm_device_list_t::     init();
  dm_radio_list_t::      init();
  dm_network_ssid_list_t::init();
  dm_radio_cap_list_t::  init();
  dm_op_class_list_t::   init();
  dm_bss_list_t::        init();
  dm_sta_list_t::        init();
  dm_policy_list_t::     init();
  dm_scan_result_list_t::init();
}
// Called BEFORE m_db_client.init() so tables exist
// before the MariaDB connection is established.

load_tables() — Populate from DB

int load_tables() {
  // SELECT * → sync_db() per row for each table
  if (dm_network_list_t::load_table(m_db_client) != 0)
    return db_cfg_type_network_list_update;
  if (dm_device_list_t::load_table(m_db_client) != 0)
    return db_cfg_type_device_list_update;
  // … radio, bss, sta, policy, op_class …
  if (is_table_empty(m_db_client)) return -1;
  set_initialized();
  return 0;
}

// Empty DB → run seed script → reload
if (rc == -1) {
  std::system("/usr/ccsp/EasyMesh/setup_mysql_db_post.sh");
  rc = load_tables();
}

If MariaDB tables are empty on first boot, the controller auto-runs the seed script, then calls load_tables() a second time. If the second load still fails, init() returns -1 and the process exits.

update_tables() Orchestration

int update_tables(dm_easy_mesh_t *dm) {
  // Network
  dm_network_list_t::update_db(
    *m_db_client, dm_orch_type_db_update,
    dm->get_network_info());

  // Device
  dm_device_list_t::update_db(
    *m_db_client, dm_orch_type_db_update,
    dm->get_device_info());

  // Radios (per radio)
  for (int i = 0; i < dm->get_num_radios(); i++)
    dm_radio_list_t::update_db(
      *m_db_client, dm_orch_type_db_update,
      dm->get_radio(i)->get_radio_info());

  // BSS, STA, OpClass, ScanResult …
}

db_cfg_type_t — Dirty Flags

Each table has a corresponding flag bit. The orchestration layer tests these to skip tables that have not changed, avoiding unnecessary SQL traffic.

db_cfg_type_network_list_update
db_cfg_type_device_list_update
db_cfg_type_radio_list_update
db_cfg_type_bss_list_update
db_cfg_type_sta_list_update
db_cfg_type_policy_list_update
// … one per table

delete vs update vs create

The caller selects dm_orch_type_db_delete, dm_orch_type_db_update, or dm_orch_type_db_create. Each list class translates this to the appropriate SQL in its update_db() override.

In-Memory Model

dm_easy_mesh_t — Per-Network Container

While dm_easy_mesh_ctrl_t owns the DB tables, the live in-memory state for each active mesh network lives in dm_easy_mesh_t instances (one per managed network).

class dm_easy_mesh_t {
  // Scalar state
  em_network_info_t    m_network;
  em_device_info_t     m_device;

  // Arrays
  dm_radio_t           m_radio[EM_MAX_RADIOS];
  dm_bss_t             m_bss[EM_MAX_BSS_PER_RADIO * EM_MAX_RADIOS];
  dm_network_ssid_t    m_network_ssid[EM_MAX_NETWORK_SSID];
  dm_op_class_t        m_op_class[EM_MAX_OP_CLASS];
  dm_policy_t          m_policy[EM_MAX_POLICIES];

  // STAs — hash map for O(1) lookup
  std::unordered_map<mac_address_t, dm_sta_t*> m_sta_map;
  std::map<mac_address_t, dm_sta_t*>          m_sta_assoc_map;
  std::map<mac_address_t, dm_sta_t*>          m_sta_dassoc_map;

  // Helpers
  em_radio_info_t* get_radio_info(int idx);
  unsigned int     get_num_radios();
  unsigned int     get_num_policy();
  bool has_policy_type(em_policy_id_type_t t);
};

Controller vs Agent Usage

dm_easy_mesh_t is shared code. The controller uses it as the in-memory representation that the DB is sync'd to/from. The agent uses it as a local cache of topology received from the controller, with no DB involvement.

STA Tracking Maps

  • m_sta_map — all known STAs (O(1) MAC lookup)
  • m_sta_assoc_map — currently associated STAs
  • m_sta_dassoc_map — recently disassociated STAs (for history)

Policy Helper

has_policy_type(t) lets send_policy_cfg_request_msg() skip TLV construction for policy types not present in the command data model — enabling incremental policy updates without re-sending unchanged TLVs.

Integration

JSON Serialisation & TR-181 Bus Integration

JSON In/Out via set_config / get_config

Every entity implements decode(cJSON*, void*) and encode(). The controller ingests JSON commands from the northbound interface (CLI / WebUI) and maps them to DB rows.

// Inbound — JSON → DB
set_config(db_client, json_obj, parent_id)
  → entity::decode(json_obj, parent_id)
  → update_db(client, dm_orch_type_db_create, data)

// Outbound — DB → JSON
get_config(db_client, parent_id)
  → entity::encode()
  → returns cJSON* tree

TR-181 Bus Handlers

dm_easy_mesh_ctrl_t registers bus get/set callbacks for every TR-181 parameter path:

  • network_get / device_get
  • radio_get / radio_tget
  • bss_get / bss_tget
  • ssid_get / rcaps_get
  • sta_get / policy_get
  • X_AIRTIES_UnassociatedStaLinkMetricsQuery() new

Handlers read from the in-memory model (not from SQL at query time) to keep latency low.

UnassociatedStaLinkMetricsQuery
Takes OpClass + one or more Channel.N.{Channel, STA.M.MAC} params. Validates inputs, builds a wfa-dataelements:UnassocSTAQuery JSON subdoc, and enqueues it as an em_cmd_t for the orchestration loop.

Thread-Safety Note

The DB client interface explicitly documents that implementations are not required to be thread-safe. The orchestration loop is single-threaded by design.

Summary

Key Takeaways

1. Single Concrete DB Backend

db_client_t is a concrete MariaDB wrapper with MYSQL *m_con. Owned by value in dm_easy_mesh_ctrl_t. All 10 list classes call it by reference. MySQL header is conditionally included for OpenWRT/RDKB vs Debian.

2. Entity + List Split

Pure-domain dm_*_t classes are shared with the agent. DB-aware dm_*_list_t subclasses are controller-only. Zero persistence overhead on the agent side.

3. Unified Controller Object

dm_easy_mesh_ctrl_t inherits all 11 list classes via C++ MI — a single object that can query, update, or delete any table without any additional glue code.

4. Dirty-Flag Driven Sync

db_cfg_type_t bitmask tracks exactly which tables changed. update_tables() skips clean tables — minimising SQL round-trips during high-frequency topology updates.

5. 10 Tables, Clear Hierarchy

NetworkList → DeviceList → RadioList → Capabilities → BSSList → STAList
NetworkSSIDList · PolicyList · OperatingClassList · ScanResultList

6. JSON ↔ DB ↔ 1905.1 Pipeline

Northbound JSON commands flow through set_config → update_db → dirty flags → 1905.1 TLV construction. Southbound telemetry flows the other way via sync_db and TR-181 bus handlers.

7. Recent Additions (develop branch)

RDKBWIFI-555 — Assoc frame IE offset
dm_sta_t::get_assoc_frame_ie_offset() probes the three possible layouts (assoc, reassoc, IEs-only) to find where IEs start. Fixes misparse of capabilities for reassociating STAs.

RDKBWIFI-529 — Stable capability decode
decode_sta_capability() is now called inside TR-181 sta_get / sta_tget before derived fields are read. Fixes alternating empty HTCapabilities under polling.

RDKBWIFI-408 — Unassoc STA query
X_AIRTIES_UnassociatedStaLinkMetricsQuery() TR-181 method added. Accepts OpClass + channel/STA lists, builds UnassocSTAQuery JSON, enqueues as em_cmd_t.
